Findings
B-671-1 — src/packages/trials/trial-usage.service.ts:264-310 (`markStarted`, insert-collision branch). When no row exists for the purchase, two concurrent starts of the same purchase both read `own = null` and both insert. The loser's `skipDuplicates` insert returns 0, it reads the `(client, coach)` holder, finds its own purchase's `started` row, and still returns `'conflict'` (:307-310). The method's contract is "reports a conflict when another purchase holds it" (:236-238), and `reserve` already handles the same-purchase case (:186). Once T3 wires it, `'conflict'` records a PackageTrialConflict and cancels the subscription after commit (#673 checkout-webhook-handler.service.ts `applyTrialState`, which runs before the CoachPackage FOR UPDATE lock). So a legitimate trial is cancelled when, for example, `customer.subscription.updated` and `invoice.paid` for one subscription are processed at once. The no-reservation path is the one the recurring native checkout (#680) uses until the stacks are integrated.
  Counterexample (CI-lane run https://github.com/BradleyGleavePortfolio/growth-project-backend/actions/runs/37173511118, `test/audit-opus-t12-116-671.spec.ts` on this head: 2 red as expected, control green): `Promise.all([markStarted(start), markStarted(start)])` with an empty ledger returns `["owned","conflict"]` with one started row for that purchase. Control: a different purchase in the same race still gets `conflict`. Independently reproduces Sol's B-671-1 on this head.
  Minimal fix rule: after a skipped insert (and after a lost released-row takeover), re-read the holder; if `holder.purchase_id === args.purchaseId` and status is `started`, return `'owned'` (refresh `trial_ends_at` as in :244-251); if it is this purchase's `reserved` row, apply the existing CAS. Report `'conflict'` only for a different purchase. Keep the probe, and add the takeover variant.

C-671-1 — src/packages/trials/trial-view.ts:80-95. A purchase whose trial never started reads `state: 'ended'` ("The trial is over"). Counterexample (same run, red): `purchaseTrialView({ status: 'pending', entitlement_active: false, trial_days: 7, trial_ends_at: null, ... })` returns `ended`. That row shape is what a checkout reservation writes (recurring #680's reserve stores `trial_days` on a `pending` row), and T3's `listForClient` lists every purchase. No mobile code reads `purchases[].trial` yet, so nothing shows this today. Minimal fix rule: `ended` only for a trial that started (trial_ends_at set and passed, or a started usage row); a never-started attempt reads `none` (or `setup_incomplete` while its checkout is open), with a test for pending / incomplete_expired.
C-671-2 — piece boundary (test/b-trials-one-trial-rule.spec.ts, test/utils/trial-fakes.ts). T1 ships trial-copy, trial-view, trial-rules and trial-diagnostics with no T1 test (the one T1 spec covers the usage ledger and capability); their tests arrive in T2/T3. The in-memory fakes model unique keys and CAS but not the CHECK constraints or real Postgres concurrency, so no test runs reserve() against reserve() on a live database. Acceptable under land-as-one (rule 11). Minimal fix rule: before T3 lands on main, add live-Postgres concurrency cases in a live-test lane: two parallel reserve() for one client and coach (exactly one `reserved`), and two parallel markStarted() for one purchase in separate transactions (both `owned`).
C-671-3 — src/packages/trials/trial-copy.ts:6-19. `formatTrialAmount` divides by 100 for every currency, so a zero-decimal currency prints the wrong amount (`formatTrialAmount(4900, 'jpy')` gives "¥49" for ¥4,900). Package currency accepts any 3-letter code (packages.service.ts:675). Minimal fix rule: use the currency's minor-unit exponent (Intl `resolvedOptions().maximumFractionDigits`), or restrict trials to 2-decimal currencies.
