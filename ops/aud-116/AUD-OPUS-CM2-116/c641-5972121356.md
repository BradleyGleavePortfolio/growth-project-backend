**B-641-12 — concurrent reversals of two refunds on one transfer lose one reversal in the books the Money read model shows**
- **Where:**
  - `recordReversal` (transfer-orchestrator.service.ts:251-280) reads the ConnectTransfer row and writes the absolute value `reversed_amount_cents: newReversed` (:258-265).
  - `SplitLedgerService.applyReversal` (split-ledger.service.ts:126-152) does the same on `reversed_cents` (:134-145).
  - Each runs in a transaction whose only lock is that refund's own ChargeRefund claim, so two different refunds never serialize.
  - Under Postgres READ COMMITTED a plain SELECT takes no row lock. Both transactions read the same value, the second UPDATE waits for the first, then writes its stale absolute value.
  - The comment at :251-252 ("Re-reads the row so a concurrent reversal of a different refund is added to, never overwritten") claims the opposite.
- **Who races:**
  - the 15-minute retry sweep for refund A against a webhook or the admin refund for refund B;
  - `charge.refunded` against `charge.refund.updated` for two partial refunds;
  - a refund against the dispute path, which uses the same read-then-write at refund-dispute-handler.service.ts:1036.
- **Impact:** Stripe made both reversals, but the local `reversed_amount_cents` and `reversed_cents` keep only one.
  - The coach Money read model reports `kept = amount_cents - reversed_cents` (coach-money.service.ts:313, :339), so it overstates what the coach kept and understates refunds.
  - `owedHeadCoachReversal` (:591) then caps later refunds against a remaining amount that is too high.
- **Probe:** red, [ci-lane run 37142381900](https://github.com/BradleyGleavePortfolio/growth-project-backend/actions/runs/37142381900). It runs the real `TransferOrchestratorService` and `SplitLedgerService` over a double whose transactions overlap (no read lock, literal UPDATE, as READ COMMITTED does).
  - The sequential control records 100 + 50 = 150.
  - Concurrent: Stripe made 2 reversals, but `ConnectTransfer.reversed_amount_cents` received 50 (expected 150) and `SplitLedgerEntry.reversed_cents` received 50 (expected 150).
  - Probe source: `ops/aud-115/AUD-OPUS-MONEY-2/audit-opm2-641-reversal-lost-update.spec.ts`.
- **Fix rule:** make the local reversal additive at the database. Use either:
  - `SELECT ... FOR UPDATE` on the ConnectTransfer and SplitLedgerEntry rows (via `$queryRaw`) before the read in `recordReversal` and `applyReversal`; or
  - one `UPDATE ... SET reversed = LEAST(amount_cents, reversed + $amount)` with status and reversed_at derived in SQL.

  Then add a live-DB test (rls-live lane) with two concurrent reversals of different refunds on one transfer, asserting the sum.
