### C findings (optional hardening; neither is reachable from the current ci.yml)
- **C-694-3: `needs:` on build-and-test is not pinned.**
  - The gate spec (:172-181) rejects job-level `if:` and `continue-on-error`. A job with `needs: [x]` is still skipped when x fails or is skipped, and GitHub says such a skipped required job may not block merging ([Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)).
  - Counterexample: GAP1 in lane 37177952064 adds `needs: [rls-floor-guard]` to build-and-test, and the guard reports no violation.
  - The same gap exists for all 11 required checks in `test/ci/branch-protection-checks.spec.ts`, which pins only `if`.
  - Fix rule: reject `needs` on build-and-test, or require every needed job to be unconditional and itself required. The best place is next to the existing `if:` assertion in branch-protection-checks.spec.ts, so it covers every required check.
  - How to verify the fix: GAP1 must go red.
- **C-694-4: the guard is static, so it cannot see anything that changes at runtime.**
  - GAP2: a Type-check env of `PATH: ./scripts/aud-fake-bin:/usr/bin:/bin` would let a repository file stand in for `npx`.
  - GAP3: an earlier step that runs `sed -i 's/"strict": true/"strict": false/' tsconfig.json`.
  - The guard stays green on both. Earlier steps that write `$GITHUB_ENV` or `$GITHUB_PATH` are in the same class.
  - Cheap partial fix: allow only `NODE_OPTIONS` among the Type-check step's effective env keys (step, job and workflow), and reject any earlier build-and-test step whose run mentions `tsconfig`, `GITHUB_ENV` or `GITHUB_PATH`.
  - The rest stays an accepted residual risk, covered by the T4 review of any ci.yml change.
