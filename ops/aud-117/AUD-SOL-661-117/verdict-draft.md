### B-661-3 — successful settlement is still neither a durable witness nor guaranteed recovery

**Where:** `src/checkout/checkout-webhook-handler.service.ts:79–109,1107–1125,1277–1301`. The witness is only `(purchase id,status,updated_at)`; a confirmed success on an already-entitled purchase writes only `updated_at: new Date()`, and success on a previously activated hosted purchase that has become `payment_failed` performs no restoration. [Exact-head settlement and failure implementation](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/6fdc35de61a26a0c9e8b3741044a3ec223dc9ab4/src/checkout/checkout-webhook-handler.service.ts#L1107-L1140)

**Executed counterexample 1 — timestamp equality:** a provisionally paid/entitled hosted purchase is witnessed before an old failure's provider lookup returns `requires_payment_method`; its PI then succeeds and the success handler executes its new timestamp write. If the application-clock millisecond equals the witness timestamp, neither `sameVersion` nor the destructive write predicate detects the success. The delayed old delivery is acknowledged and commits **payment_failed / entitlement false**. The paired control with a timestamp only one millisecond newer correctly throws 503 and preserves paid access; the fixture compares distinct Date instances by their timestamp, like the DB predicate, rather than by JS object identity. [Independent actual-handler proof and control](https://github.com/BradleyGleavePortfolio/growth-project-backend/actions/runs/37177635617)

**Executed counterexample 2 — hosted recovery:** start with the explicitly supported already-completed provisional hosted purchase (`stripe_checkout_session_id='cs_r4'`, PI bound); a real provider-confirmed failure commits `payment_failed`/unentitled; the same PI subsequently succeeds. Round 4 returns `checkout_session_activates`, updates zero entitled rows, leaves **payment_failed / unentitled / card_declined**, and the success is consumed. Its owning session already completed; recovery cannot depend on another completion or duplicate purchase fanout. This reproduces the prior B-661-3 acceptance gap using a valid hosted-session identity, not the prior probe's omitted field. [Independent hosted recovery proof](https://github.com/BradleyGleavePortfolio/growth-project-backend/actions/runs/37177635617) [Prior accepted invariant](https://github.com/BradleyGleavePortfolio/growth-project-backend/pull/661#issuecomment-5976137883)

**Minimal fix rule:** record collision-free, transactionally authoritative successful-settlement/activation evidence for the owning PI, not an application-clock timestamp alone. An older failure must CAS against that evidence and never revoke a confirmed success; a success that follows a real failure of an already-completed hosted purchase must recover that purchase and its access without re-running first activation/fanout/splits. Keep the never-activated adopted-hosted guard, ordinary genuine async failures, PaymentSheet retry and all Stripe HTTP outside the DB transaction.

**Verify:** retain the equal-clock/newer-clock pair, prior stale-prefetch ordering, provisional-already-paid success, and completed-hosted failure→same-PI success. Add real fanout/drop recovery assertions and a never-activated adopted-hosted control; do not declare the old hosted acceptance invalid merely because the new predicate now ignores its success.

### B-661-8 — a retried success still resurrects a purchase terminated after its read

**Where:** `src/checkout/checkout-webhook-handler.service.ts:1107–1109,1128–1140`: a claimable `pending`/`payment_failed` snapshot is read, but the consequential success write uses only `{id}`; neither the claimable status, owning PI nor the observed version is rechecked at write time. This is in the changed success lifecycle, not a finding assigned to the separate refund PR. [Exact-head read/write boundary](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/6fdc35de61a26a0c9e8b3741044a3ec223dc9ab4/src/checkout/checkout-webhook-handler.service.ts#L1107-L1140)

**Executed counterexample:** a never-activated PaymentSheet retry is `payment_failed`; `payment_intent.succeeded` reads that claimable row; a full-refund transaction commits `refunded`/unentitled before the success write. The id-only write then commits **paid / entitlement true**, despite the refund. The existing refund implementation can make exactly that independent terminal write, and this purchase has no earlier fanout marker to accidentally abort its first activation. A refund already present before the success read is safe; the missing boundary is specifically read→intervening terminal write→success activation. [Independent actual-handler race proof](https://github.com/BradleyGleavePortfolio/growth-project-backend/actions/runs/37177635617) [Real full-refund writer](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/6fdc35de61a26a0c9e8b3741044a3ec223dc9ab4/src/checkout/refund-dispute-handler.service.ts#L225-L231)

**Minimal fix rule:** acquire authoritative ownership of activation at the success write: recheck the owning PI plus claimable status/version under the same transaction, handle a lost claim by re-reading/no-op or rollback/redelivery, and run first-payment/fanout/deferred split only for the winner. Terminal refund/dispute/cancel/expiry/deletion must remain authoritative; do not rely on a read fence or eventual delivery to restore it.

**Verify:** preserve the refund-before-read no-op and ordinary failed→success control; add the interleaving above for refunded/canceled/expired/disputed/chargeback_lost and concurrent success claims, with no duplicate fanout/split.
