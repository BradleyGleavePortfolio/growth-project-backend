## Must fix

### B-345-1 — inherited B-329-5: write-ahead admission starts a create after its originating form/session retires

`src/lib/coachSetup/packageCreateIntent.ts:267–280,289–303,324–334` accepts only a captured coach ID, not a live account/session/mount predicate; after `await saveIntent`, it invokes `onIntent` and dispatches create, and later create/update completions can invoke callbacks or follow-on updates without rechecking ownership. [Affected helper](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/a4e4958820053b5aaa0f2d4a8c14f140816541b2/src/lib/coachSetup/packageCreateIntent.ts#L267-L336).

**Counterexample:** hold actual-form write-ahead storage, unmount before any network create, then resolve storage: the actual S1 helper dispatches one create where zero was allowed; the new S2 actual-form probe reproduces this at a byte-identical S1 helper, independently of the original two owner/unmount failures. [Current executed assertion](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37179741603/job/111369708813), [original owner/unmount proof](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37143533028).

**Minimal fix:** carry a live originating account/session generation plus mount/operation predicate into the helper; recheck after each awaited persistence/network boundary and before every subsequent create/update or memory callback, and keep the saved identity recoverable on cancellation rather than clearing it or starting another request. Verify held-write unmount and account-replacement tests fail before/pass after, and wire every actual caller in its owning slice.

### B-345-2 — changed-input replay falsely accepts a billing cadence the actual PATCH never sends

`src/lib/coachSetup/packageCreateIntent.ts:330–334` detects changed cadence, passes a full create input to update, then replaces the remembered input as though the change succeeded; however `src/api/packagesApi.ts:431–443,490–500` drops `billingInterval` and `intervalCount` from the actual PATCH, even though both the current backend and the required package-create backend accept their wire fields. [New helper update path](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/a4e4958820053b5aaa0f2d4a8c14f140816541b2/src/lib/coachSetup/packageCreateIntent.ts#L330-L350), [actual mobile adapter](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/a4e4958820053b5aaa0f2d4a8c14f140816541b2/src/api/packagesApi.ts#L431-L443), [backend update contract](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/a7b73e566c6ffc883743aa9c3a066120e0978291/src/packages/packages.controller.ts#L134-L160).

**Counterexamples:** replay a previously created monthly package after a lost response/publish failure, select one-time, then retry: the helper remembers one-time but actual PATCH contains no `billing_type`, leaving a recurring server offer; selecting free instead sends zero with the old recurring billing type and fails the backend's merged-pricing validation. Both independent assertions fail with the actual helper and actual mobile HTTP adapter, plus a contract-faithful pricing double for the free case; no live Stripe/database transaction is claimed. [Executed wire/pricing proof](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37179742309/job/111369710659), [backend merged-pricing validation](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/a5b605d1aa86f3afcece6061dc0502f20b83f27e/src/packages/packages.service.ts#L177-L240).

**Minimal fix:** align the PATCH mapper with supported `billing_type`, `billing_interval`, and `billing_interval_count`, including one-time clearing, and reconcile the actual returned configuration before remembering/reporting it as selected. Add monthly↔one-time, paid→free, cadence/count and lost-response replay regressions using the real adapter, not a mocked `update`.

### B-345-3 — unknown-error diagnostics violate the content/reference boundary

`src/lib/coachSetup/errors.ts:83–85,203–219` forwards the original untrusted exception to Sentry and obtains a reference only from a server response; a local/transport failure without one produces `requestId: null`, while arbitrary exception text is not removed by the current exception-value/URL scrub path. [New diagnostic call sites](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/a4e4958820053b5aaa0f2d4a8c14f140816541b2/src/lib/coachSetup/errors.ts#L203-L219), [capture boundary](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/a4e4958820053b5aaa0f2d4a8c14f140816541b2/src/services/sentry.ts#L165-L179), [existing scrub policy](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/a4e4958820053b5aaa0f2d4a8c14f140816541b2/src/services/sentryScrub.ts#L16-L39).

**Counterexamples:** an unknown local error returns no support reference, and a synthetic exception containing an email-like marker reaches `captureError` with that marker unchanged; both executable assertions fail, proving the call-site boundary rather than claiming live telemetry was sent. [Executed diagnostic assertions](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37179742309/job/111369710659).

**Minimal fix:** report a bounded content-free diagnostic (fixed error/category plus allowlisted codes/status) instead of raw exception text/config/body; use the existing correlation helpers to reuse or generate one diagnostic reference, tag that same reference in Sentry, and display its short form plus the support path. Verify email/message/body sentinels never reach the capture boundary and no-reference failures have the same attributable reference in UI/reporting.
