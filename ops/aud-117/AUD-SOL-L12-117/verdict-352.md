### B-352-1 — The payment-lockout singleton accepts another account's state

`src/services/api.ts:276-280`; `src/entitlements/dunning/dunningLockoutStore.ts:27-54`. Every matching 403 writes the process-global lock without checking the request's owning account/auth generation, and neither the store nor this new interceptor retires it on logout. The existing logout reset list omits this new store, so the previous account's signal/reference can survive until a successful later status read. ([Exact interceptor](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/58b80914feb62101aca2c7b5e8985d32912b80b0/src/services/api.ts#L271-L283), [exact store](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/58b80914feb62101aca2c7b5e8985d32912b80b0/src/entitlements/dunning/dunningLockoutStore.ts#L27-L54), [actual logout boundary/reset list](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/58b80914feb62101aca2c7b5e8985d32912b80b0/src/services/authActions.ts#L408-L440))

**Concrete CI counterexamples:** (1) handle A's lockout, emit the production logout boundary: the singleton remains locked; (2) retire A, switch to B, explicitly clear the singleton, then deliver A's delayed 403 with A's Authorization header: B's singleton becomes locked again and retains A's request reference. Both assertions fail against the actual registered response interceptor/store; current-account LOCKED_DUNNING and unrelated-403 controls pass, as does the existing interceptor suite: **2 failed / 4 passed**. This can put a paid next user behind the lockout and suppress their entitlement sheet, especially while B's status read is offline; resetting alone does not fix the delayed-response case. ([Independent CI probe](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37179751151), [downstream consumer in L2](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/e22acc84b3ee99c94f3ec77793b38ca0c8157241/src/entitlements/EntitlementProvider.tsx#L167-L172))

**Minimal fix rule:** make the lock signal account/auth-generation owned, clear/retire it synchronously at the actual logout/account-transition boundary, stamp originating requests with their generation, and discard retired-generation 403s before any global write. Token refresh within the same account must continue working; do not use raw JWT equality as the account identity. Add failing-before/passing-after tests for logout, A→B, delayed old responses after an explicit reset, and valid same-account refresh. Coordinate the provider's own async retirement fence in #353; this finding belongs to L1's signal/transport, not to the other PR's UI. ([Affected L1 code](https://github.com/BradleyGleavePortfolio/growth-project-mobile/blob/58b80914feb62101aca2c7b5e8985d32912b80b0/src/entitlements/dunning/dunningLockoutStore.ts), [paired L2](https://github.com/BradleyGleavePortfolio/growth-project-mobile/pull/353))
