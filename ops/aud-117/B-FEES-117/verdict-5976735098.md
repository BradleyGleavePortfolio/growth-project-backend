## 2. Round-11 delta

**2a. Reversal send admission (`transfer-orchestrator.service.ts:1141-1225`, `1265-1311`)**
- **The claim.** A CAS `updateMany` on `(id, status pending, attempts, last_attempt_at)` as read (`:1151-1160`). `attempts` only grows, and nothing else writes it in the F6 tree (every `transferReversalOp` writer is in this file).
- **After the claim.** The fence runs again (`:1161`), and the op is re-read: still pending, same attempt, same instant (`:1162-1171`). A lost or moved claim goes to `reversalMoved`. That returns the recorded outcome, or `ReversalUncertainError` while the op is pending, and it never sends.
- **The start budget.** Counted from before the claim await, as the larger of the wall and monotonic ages (`:1172-1178`). It is checked at `:1181` and again synchronously at the HTTP boundary through `beforeSend` (`:1192`). F1's `post()` has no await between that check and `fetch`.
- **Abandoned claims.** One that misses the budget logs `SFEE_REVERSAL_SEND_ABANDONED` and stays pending with `attempts > 0`, so the next driver lists Stripe first (W2, W6, X2).
- **Timing argument (mine).**
  - The second fence renews the lease to now + 120 s (`CHARGE_LOCK_TTL_MS`).
  - A send must start within 30 s of its claim, so at least 90 s of lease remain when the request starts.
  - A fenced takeover can therefore begin only after the request is already in flight.
  - Any later re-send of the same op uses the same key inside Stripe's 24 h window. The only exception is a request frozen inside HTTP for more than 24 h, which the new duplicate alert now reports.
- **A same-key re-send answered `409 idempotency_key_in_use` while the first request is still running.** This is not a definitive refusal (`isDefinitiveStripeRefusal` admits only 400, 402 and 404). The op stays pending, and the first request's receipt then records 400 once. There is no refusal, no recovery and no duplicate alert (my probe X1).
- **Real Postgres (DB-R1).** Two PrismaClient pools race 20 undriven ops (`attempts 0`, `last_attempt_at NULL`). Result: exactly 1 Stripe send per op, 20 losers that are all `ReversalUncertainError`, and 400 recorded once per op.
- **TIMESTAMP(3) round trip (DB-R2).** An op claimed earlier at `...00.123Z` is re-claimed, sent once, and ends `attempts 2`.
- **The duplicate alert.** When `completeReversal` loses its CAS to a receipt naming another Stripe reversal, it logs `SFEE_REVERSAL_DUPLICATE alert=true` with ids and cents only (`:1295-1309`). The ordinary same-id race raises no alert (D1). A refused-in-the-books case names `status=refused recorded_stripe_reversal=none` (D2).

**C-682-5: two Stripe reversals for one op key complete silently while the op is pending.**

- **Fix rule:** scan the whole listing. When more than one reversal matches, complete with one and log `SFEE_REVERSAL_DUPLICATE` with every id and the extra cents.

**C-682-6: the 160-character cut drops trailing words, never amounts.** This is a correction of the 116 draft, which said the cut lands inside an amount.
- **Where:** `payout-notice-copy.ts:117`. The cut logic is from round 5; round 11 changed the strings it cuts.

  - `amount_cut=0`.
  - USD never truncates up to $999,999.99.
- **Why C:** email and the Money page show the full text, and the shape is rare.
- **Fix rule:** when the body is over the limit, drop or shorten whole clauses. For example, use "The {released} hold was released." alone, or a shorter held sentence. Never cut mid-word.

**C-682-7: the `send_abandoned` cause text points at another attempt.**

- **Fix rule:** give each reason its own cause text, for example "this worker's claim was not started inside the start budget; the op stays pending and the next driver lists Stripe first".
