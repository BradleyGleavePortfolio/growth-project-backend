## Design notes for auditors

- `readPurchaseVersion` / `lockPurchasesOfPaymentIntent` / `wasActivated` return a neutral answer for doubles without `$queryRaw` / `purchaseFanout` (version null -> retry; no lock; not activated). Production clients always have them.
- Order in `applyPaymentIntentFailed` (settled branch): witness present for this purchase -> Stripe status (null 503, unreadable no-op, completed/processing `stale_failure`) -> only a not-completed status reaches the locked version check and the revoke.
- Recovery is keyed on the PurchaseFanout row; it is written in the activation transaction (fanout errors roll the activation back) and nothing deletes it while the purchase exists.
- C-661-10 composition: if the metadata fallback stamped one PaymentIntent on two rows, `findFirst` may return the adopted (never-activated) row and skip recovery of the other; both rows are locked and every write is fenced on its own state, so nothing is overwritten.
