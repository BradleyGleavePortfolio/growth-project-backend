## For the operator (code outside #689/#690)
1. **#688 (D2), v1 `DunningService.recordResolution`.** It has no tx parameter and no dispute guard. Both D3 (after the locked check commits) and D4 (after the check) call it on `this.prisma`. A dispute recorded in the milliseconds between the check and v1 is left on a resolved cycle. The fix is for `recordResolution(purchaseId, tx?)` to join the caller's tx under the DunningState lock and re-check the obligation. A lock taken on the webhook tx would deadlock against today's v1 call on a second connection, which is why D4 takes none.
2. **#688 (D2), `resolvePurchaseFromCharge`.** It swallows errors and returns null, so `onDisputeClosed` answers `purchase_unresolved`, which is acknowledged, on a transient DB or Stripe failure. Now that dispute effects fail the delivery, that helper should throw so the event is redelivered.
3. **#688 (D2), sweep.** It skips locked rows (`locked_out_at: null`), so it never repairs a locked cycle whose won-dispute effect was lost (the second half of Opus C-690-2). That is lower risk now that effects are redelivered.
4. **#687 (D1), `src/email/templates/dunning-v2-client.hbs:9`.** It still says "the amount owed is paid with it and your access stays on". That is the same untrue promise fixed on the card page here.
5. **Coupling, for awareness.** A v2 dispute effect that fails persistently now fails the whole dispute event, including v1 refund/dispute handling, until Stripe stops retrying (about 3 days). Flag off: no change.
6. **Pre-existing main log lines.** prefetch, fanout, split, terminate and customer.updated in the webhook handler still log `err.message`. They are not new in D4 and were left as they are.
