### B-659-1 — editing a paused broadcast that already ran sends it to everyone again (double send), and a single run mixes two bodies
- **Evidence:**
  - `EDITABLE = {draft, scheduled, paused}` (`broadcasts.service.ts:21`). `pause` is allowed from `sending` (`:313-316`).
  - `update` (`:259-301`) does not look at runs or `occurrences_sent`. It rewrites `body` / `segment` / `card` and sets `next_run_at = firstRun(v, now)`, which for a one-off is `now` or `send_at` (`:170-176`), keeping `paused`.
  - `resume` for a one-off then sets `status: 'scheduled'` with that `next_run_at` (`:325-336`).
  - `claimDue` creates a second run with a new `run_key` (occurrence ISO), so the unique `(broadcast_id, run_key)` does not collide (`broadcast-dispatcher.service.ts:117-160`).
  - `fanOutRun` inserts deliveries for the whole segment again. Every client who already got the first run gets the message a second time.
  - Separately, the first run's remaining deliveries read `b.body` / `b.card` at send time (`dispatcher :366-373`). After the edit, one run sends the old text to some recipients and the new text to others.
- **Path:** a coach sends to 300 clients, notices a typo mid-send, taps Pause, fixes the text and taps Resume. Everyone already reached gets it twice, and the rest get a different text. That breaks the "never double-send" property this PR states for T4.
- **Minimal fix:**
  1. Snapshot `body` + `card` onto the run at fan-out (or onto each delivery) and send from the snapshot, so an in-flight run is immutable.
  2. In `update`, refuse a one-off once it has any run, with a specific code (for example `broadcast.already_sending`: "This message has started sending, so it cannot be edited. Cancel it and send a new one."). For recurring broadcasts, apply the edit from the next occurrence only and never re-anchor into an occurrence already sent today.
  3. Add tests: pause mid-run, edit, resume. No recipient gets two messages, and every delivery of a run carries the same body.
