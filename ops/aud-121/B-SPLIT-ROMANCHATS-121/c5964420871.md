### A-331-7 — refresh of signed-out A can overwrite signed-in B's credentials during its awaited SecureStore write

`src/services/api.ts:188–223` reads the old refresh token, calls Supabase, then checks stored refresh-token equality at `:210`. It subsequently **awaits** `secureStorage.setItem('supabase_token', A)` at `:216` before updating the refresh token, without another ownership/epoch guard. B can sign in during that async write. An audit-only real interceptor + Roman API + storage/adapter probe pauses A's token write, switches to B, and resumes: B's access token becomes A's while B's refresh token remains B's. The old Roman request is correctly dropped, but B's subsequent *unbound* API calls now run under A's credentials. This is an auth/tenancy break introduced by the fix round's shared refresh change and requires an atomic/serialized session replacement, not another read-only check before `setItem`. [Refresh path](https://github.com/BradleyGleavePortfolio/growth-project-mobile/pull/331).

**Minimal fix:** serialize sign-in/sign-out/token replacement with refresh commit, or use an SDK/session primitive with a genuine compare-and-swap guarantee; the old refresh may not publish either token once a new sign-in starts. Test a sign-in at every awaited read/write boundary, plus same-account new sign-in, and prove both stored tokens and the next ordinary API request belong to B. [Candidate transport and binding](https://github.com/BradleyGleavePortfolio/growth-project-mobile/pull/331).

### B-331-8 — failed old refresh can sign out the new session while checking its deletion receipt

`src/services/api.ts:210–215,225–259`: a failed A refresh passes the single stored-token equality check, then `handleRefreshFailure()` awaits the deleted-account receipt (`:239–240`) **before** calling `signOut()` (`:249–256`). If B signs in during that await, the pending A failure signs B out. The independent real-client probe pauses the receipt request, switches to B, resumes, and observes `signOut` called once and B's stored token removed. The `AccountChangedError` exception at `:210` cannot prevent a session change after that check. [Failure path](https://github.com/BradleyGleavePortfolio/growth-project-mobile/pull/331).

**Minimal fix:** bind failure cleanup to the same initiating session and fence it immediately before destructive sign-out, with serialization against concurrent sign-in (a check before another asynchronous gap alone is insufficient); add this interleaving test and assert B remains signed in. Also cover an A→logout→A generation change. [Candidate refresh tests](https://github.com/BradleyGleavePortfolio/growth-project-mobile/pull/331).
