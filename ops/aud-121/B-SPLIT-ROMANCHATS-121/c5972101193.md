### B-331-9 (new): a refresh that starts while a sign-in or sign-out write is still in flight commits the old account's token
- **Where:**
  - `api.ts:406` captures `startGeneration = sessionGeneration()` when the 401 arrives.
  - `sessionFence.ts:67` bumps the generation when a write is *called*, not when it lands.
  - `holdSessionFence` (`:80-81`) checks only `generation === expected && holder === null`.
- **The gap.** A sign-in or sign-out whose last native write is still in flight has already moved the generation. A stale 401 from A that arrives in that window therefore starts a refresh that adopts the new generation as its own.
  - The refresh then reads A's refresh token, because B's write has not landed.
  - Its check read (`:245`) still sees A's token, so `holdSessionFence` succeeds and A's refreshed access token is written.
  - The in-flight write then lands on top, leaving a mixed pair.
- **Executed probe (CI lane, PR head plus the probe spec only).** [Run 37143283737](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37143283737) on `audit/AUD-OPUS-MOB-CORE/331-r2-inflight` uses this PR's own harness: real axios client and interceptors, real `secureStorage` and `sessionFence`, and the pausable SecureStore double. Result: 2 failed, 1 passed.
  - **P1.** `/a-work` is sent with A's token, then B signs in with B's refresh-token write held in flight, then A's 401 arrives. The stored access token is A's refreshed token and the refresh token is B's. B's next unbound request goes out with A's credential. This is the same cross-account swap as A-331-7, through a new interleaving.
  - **P2.** Sign-out's refresh-token removal is held in flight, then A's stale 401 arrives. After sign-out, A's refreshed access token is stored again. `RootNavigator.tsx:416` reads that key to decide whether the person is signed in, so on a shared device A comes back after signing out.
  - **Control.** An ordinary same-session 401 still refreshes and replays (pass).
- **Probability.** In production this needs a Keychain/Keystore write that is still unfinished when the refresh's check read is issued, so it is narrow. But the PR states the guarantee in the shared transport, and the failure is a credential swap or a resurrected session.
- **Minimal fix (no feature change):**
  1. Count unfenced session-key writes in flight in `sessionFence`. Increment in `beforeSessionWrite`, and decrement in a `finally` after the native op in `secureStorage.setItem/removeItem` (and in the legacy migration write at `secureStorage.ts:54` for session keys).
  2. `holdSessionFence` returns null while that count is above zero.
  3. `readTokenForRequest` treats count > 0 like a generation change: re-read, or refuse after the bounded retries.
  4. Defence in depth: start the refresh only for the generation the failing request was sent in. If `originalConfig._sessionGeneration !== sessionGeneration()`, do not refresh; reject with the original 401, or `AccountChangedError` when bound.
  5. Add P1 and P2 as failing-before tests, plus a sign-in whose *access*-token write is in flight, and keep the same-session control.
