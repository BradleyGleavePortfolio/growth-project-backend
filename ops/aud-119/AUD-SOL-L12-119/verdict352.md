### B-352-3 — A retired native initialization can replace the next account's sheet

`src/entitlements/dunning/updateCard.ts:180-198`. Inside one `guarded` closure, `await sdk.initStripe(...)` is immediately followed by `sdk.initPaymentSheet(...)`; the ownership predicate is checked only after both calls. Hold A's `initStripe`, retire A, then initialize B's sheet; releasing A still initializes the module-owned sheet with A's customer, ephemeral key and SetupIntent before returning `retired`. This is a new native-state write after retirement, not a claim that an already-sent server request was canceled. ([Candidate helper](https://github.com/BradleyGleavePortfolio/growth-project-mobile/pull/352), [retired-init assertion proof](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37229539410), [shared native SDK implementation](https://github.com/stripe/stripe-react-native))

The independent two-owner SDK-state probe models the installed 0.64.0 native module's single PaymentSheet: B initializes its customer while A's initialization is held; A then replaces it, so B's subsequent presentation observes A rather than B. This is boundary evidence with a SDK double, not a claimed real-device charge or server authorization bypass. **Fix rule:** re-check the initiating owner after `initStripe` and before `initPaymentSheet`, retain ownership checks around every native await, and ensure a retired/in-flight native initializer cannot corrupt a current owner's shared SDK state. Regress this two-owner order plus positive same-owner presentation; do not remove native card update/3DS/1A functionality. ([Two-owner probe](https://github.com/BradleyGleavePortfolio/growth-project-mobile/actions/runs/37229652332), [Stripe native SDK](https://github.com/stripe/stripe-react-native))
