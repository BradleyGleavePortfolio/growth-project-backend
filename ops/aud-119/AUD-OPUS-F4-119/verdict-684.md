## Findings

### B-684-7 — `refund.updated` never reaches the refund handler; the async-refund fix rests on a deprecated event
- Where: `src/checkout/checkout-webhook-handler.service.ts:219-227` routes `charge.refunded` and `charge.refund.updated` (not `refund.updated`) to `refundDispute.handle`; any other type hits `default: return { claimed: false }` (:260-261). Round 13 added `case 'refund.updated'` only inside `refund-dispute-handler.service.ts:178`, which the webhook never calls with that type. Nothing else in `src` handles `refund.updated` (`rg "'refund.updated'" src`: only :178).
- Fact: Stripe lists `charge.refund.updated` as "(Deprecated) Sent when the refund is updated, only for refunds with a corresponding charge. Listen to `refund.updated` for updates on all refunds instead" ([Stripe refunds guide](https://docs.stripe.com/refunds)); the event reference says it fires "on selected payment methods" ([Stripe event types](https://docs.stripe.com/api/events/types)). FIX ROUND 13 asks the operator to subscribe the endpoint to `refund.updated`; if it does (or Stripe stops sending the deprecated event for a method), every pending -> succeeded and succeeded -> failed transition is dropped with a 2xx: the async refund never moves money (the original B-684-3 P3/P4) and a failure after apply raises no C-684-4 alert.
- Probe (lens-only branch `audit/AUD-OPUS-F4-119/684-refundstatus`, commit a8bf276c on 6b13af56, spec `test/audit-opus-f4-119-684.spec.ts`; 4,900 charge, fee 172, coach net 4,630; events go through the real `CheckoutWebhookHandlerService`): [run 37229178449](https://github.com/BradleyGleavePortfolio/growth-project-backend/actions/runs/37229178449/job/111515026132)
  - R0 control PASS: `charge.refund.updated(succeeded)` via the router: `refunded_cents` 4,900, coach 0.
  - R1 FAIL: `refund.updated(succeeded)` via the router returns `{ claimed: false }`; `refunded_cents` 0, coach keeps 4,630 while the client got 4,900 back.
  - R2 FAIL: `refund.updated(failed)` via the router: the refund row stays `pending`.
- Minimal fix rule: route `refund.updated` next to `charge.refund.updated` at checkout-webhook-handler.service.ts:220, and test at least one async refund through the router (R1/R2). Both events of one transition must stay idempotent on `ledger_reversed` (probe S3 sends the duplicate). Verify: R0-R2 pass.

### B-684-8 — a stale refund event rewrites a failed refund to succeeded and moves the coach's money
- Where: `upsertAndApplyRefund` writes `status: args.status` unconditionally (refund-dispute-handler.service.ts:562-571); the apply step under the charge lock re-checks only `ledger_reversed` (:628-631), not the status; the same-currency settlement sums the DB rows marked succeeded (`succeededRefundCents`, charge-settlement.service.ts:1443, :1689). `applyRefundUpdate` trusts the event payload's status (:494) and checks `ledger_reversed` for the C-684-4 alert outside the lock (:495). `completeRefunds` trusts an embedded list snapshot when it looks complete (:425).
- Fact: refunds are asynchronous; "a refund can appear to succeed and later fail" ([Stripe testing docs](https://docs.stripe.com/testing)), and a failed refund returns the funds to the platform balance ([Stripe ACH Direct Debit](https://docs.stripe.com/payments/ach-direct-debit)). "Stripe doesn't guarantee the delivery of events in the order that they're generated" and retries a failed delivery for up to three days ([Stripe webhooks](https://docs.stripe.com/webhooks)); this code fails deliveries on purpose (`ChargeLockBusyError`, `SFEE_REFUND_STATE_UNAVAILABLE`, `SFEE_NOTICE_UNRECORDED`). `failed` and `canceled` are terminal Refund statuses.
- Counterexample (same probe run): S1 FAIL: pending ACH refund; the `failed` update is processed; the earlier `succeeded` update is then redelivered: `refunded_cents` 4,900 and the coach is reversed 4,630 for a refund Stripe reports failed (funds back on the platform), with no alert. S2/S3 FAIL: the row is rewritten from `failed` to `succeeded` (S3 after the C-684-4 alert already fired). S4 FAIL: a failed refund recorded first, then a late `charge.refunded` whose embedded complete list still says succeeded: 4,900 moved. S5 control PASS (an unseen refund's `succeeded` update before `charge.refunded` converges once).
- Minimal fix rule: (1) a refund row in `failed` or `canceled` is terminal: no write moves it to another status, and a `succeeded` row may only move to `failed` (one guard in `updateExisting`, so every path is covered: webhook updates, `charge.refunded`, the embedded snapshot, admin refunds); (2) inside `withChargeLock`, apply only when the freshly read row is still `succeeded` and not `ledger_reversed`; (3) take the failed-after-apply decision from the row as written under that lock, so a concurrent `charge.refunded` cannot slip a reversal past the alert. Verify: S1-S4 pass, S5 and the #697 round-13 P1-P5 / C-684-4 cases stay green. Tests fit in #697 (1,831 lines).
