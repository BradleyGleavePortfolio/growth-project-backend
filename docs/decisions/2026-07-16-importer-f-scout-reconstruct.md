# ADR — IMPORTER-F: Reconstruct a Settled Crawl Intent's Staged Clients into Invite-Pending Roster Records

- **Status:** Accepted
- **Date:** 2026-07-16
- **Decision owner:** Bradley Gleave (repo owner)
- **Lane:** IMPORTER-F — backend reconstruction of staged `clients` into the D2 roster model
- **Canonical context:** D2 DECIDED (Op 59), context commit
  `c634003265cad6d087baad1dcbbeb0593bf9b4ae`
- **Affected files:** `prisma/schema.prisma`,
  `prisma/migrations/20261223000000_scout_reconstruction/{migration,down}.sql`,
  `src/scout/scout-reconstruct.dto.ts`, `src/scout/mappers/truecoach-clients.mapper.ts`,
  `src/scout/scout-reconstruct.service.ts`, `src/scout/scout-reconstruct.controller.ts`,
  `src/scout/scout.module.ts`, `src/common/feature-flag/feature-flag-not-found.middleware.ts`,
  `src/analytics/events.ts`, `.env.example`, `scripts/importer-contract.ts`,
  `docs/contracts/importer-openapi.json` (regenerated), plus co-located + contract specs.

## Context

`POST /api/scout/ingest` (IMPORTER-B) commits one `ScoutIngestEntity` row per
crawled entity, and `complete()` (IMPORTER-E) settles the run into a
`ScoutImport` with a verbatim `terminal_status`. The staged `clients` entities
are, at that point, opaque platform payloads — not yet anything a coach can act
on. IMPORTER-F is the first proving pass that turns a **settled** intent's
staged `clients` into first-class, coach-owned roster records.

D2 (DECIDED, Op 59) fixes what that target record is: an **invite-pending,
non-login, tenant-owned canonical `Person`/roster record**. No `AuthPrincipal`,
`User`, or credential is minted at import; a `Person` links to an auth identity
only later, via an explicit credential-verified claim (out of scope here).
Email is unverified imported data — it is deliberately **not stored as a column
and never used as a canonical id or linking key**. Identity is the opaque
server-issued `person_id`; dedup/idempotency is the tenant-scoped external_ref
`(coach_id, source_platform, source_person_id)`.

## Problem

Reconstruct exactly the staged `clients` of one **settled** intent into
invite-pending roster `Person` records, tenant-scoped in the data layer,
feature-flagged OFF by default, idempotent on replay, honest in its accounting,
and with no credential minted and no email used as a key — **without** racing a
still-running crawl or letting one poison row abort the batch.

## Root cause

There was no reconstruction projection over the staged entities and no target
roster model. The blocker was a missing **write projection + target table**, not
a missing read. So the fix adds the D2 `Person` roster model, a per-entity
reconciliation ledger, and a service that maps → upserts → tallies.

## Options considered

- **(a) Provision an auth `User`/credential per imported client.** REJECTED by
  D2 (Option 2). It mints login identity from unverified data, makes email a de
  facto linking key, and creates an account-takeover surface. Explicitly
  forbidden by the build gate.
- **(b) A separate staging-identity table distinct from the canonical roster.**
  REJECTED by D2 (Option 3). A second identity store that must later be
  reconciled with the canonical `Person` — duplicate storage and a guaranteed
  drift seam.
- **(c) [CHOSEN] Hardened Option 1 — invite-pending, non-login, tenant-owned
  canonical `Person`.** The imported client IS the canonical roster record from
  the start, in an `InvitePending` state, with no credential and no email key.
  A claim later attaches an `AuthPrincipal`. Additive migration, additive
  contract, flag OFF by default.

## Musk five-step result

- **Questioned:** Do we need an auth identity at import? No — D2 says a roster
  record with no credential is sufficient and safer. Do we need to store email?
  No — it is never a key and is not required to reconstruct a roster row, so it
  is not read or stored.
- **Deleted:** The `AuthPrincipal`/`User`/credential at import (D2), the email
  column and any email-based linking (D2), and any "reconstruct a running
  intent" path (a partial-roster hazard) are removed, not deferred.
- **Simplified:** One pure total mapper (`mapTrueCoachClient`) + one service
  method that, per row, upserts a `Person` on the external_ref and upserts a
  ledger row — each in its own transaction. Counts are read back from the
  ledger, so the response is a projection of durable state, not an in-memory
  tally that could disagree with the DB.
- **Accelerated:** Idempotency is structural, not procedural — both the `Person`
  (`@@unique([coach_id, source_platform, source_person_id])`) and the ledger
  (`@@unique([coach_id, intent_id, entity_type, source_id])`) are upserted, so a
  replay mints no new rows and returns identical counts with no dedup bookkeeping
  in application code.
- **Automated last:** the frozen OpenAPI slice is regenerated by
  `npm run contract:importer` and pinned byte-for-byte by the drift test.

## Idiot-index result

Theoretical minimum to satisfy the goal is "one roster table + one honest
reconciliation record, written idempotently." Option (c) is at that floor: two
additive tables, zero new writers outside this lane, one migration. No auth
tables, no credential store, no email index, no second identity model — all
removed by honoring D2 rather than re-litigating it.

## Extreme test

- **Poison row:** each staged row is reconstructed in its **own** transaction
  inside a try/catch. A row that throws (malformed payload, DB constraint) is
  recorded `failed` with a non-PII reason (`error:<ErrorName>`, never the
  payload) and its siblings still reconstruct. One bad row cannot abort the
  batch.
- **Replay (10x):** re-running a settled intent upserts the same `Person` rows
  and the same ledger rows; `staged === reconstructed + skipped + failed` holds
  identically every pass. No duplicate roster records, no count drift.
- **Running intent:** `assertSettled` rejects any intent whose `ScoutImport`
  has no terminal status (or no import row) with `409 Conflict` — reconstructing
  a live crawl would race still-arriving ingest and produce a partial roster.
- **Cross-tenant probe:** `coach_id` is taken from the **token identity**, never
  the body; every query and upsert is scoped by it, and RLS is FORCED on both
  tables (service_role PERMISSIVE, anon/authenticated RESTRICTIVE deny-all). A
  coach cannot reconstruct or read another tenant's rows.
- **Flag off:** `featureFlagNotFoundMiddleware` darks the whole `/api/scout`
  surface AND the more-specific `/api/scout/reconstruct` before any guard runs,
  so the route is indistinguishable from unmounted unless BOTH
  `FEATURE_SCOUT_INGEST` and `FEATURE_SCOUT_RECONSTRUCT` are `'true'`.

## Hyperscaler lens

- **Reliability/failure-containment:** per-row transactions bound the blast
  radius of any single failure to one ledger `failed` row; the batch is
  self-healing on replay. Counts are derived from the durable ledger, so a crash
  mid-batch leaves a consistent, resumable state.
- **Security:** no credential is ever minted; email is never read; identity is an
  opaque server id; tenant isolation is enforced in the DB (FORCE RLS) as well as
  the token-derived `coach_id`. This follows the SCIM/NIST posture that imported
  attributes are unverified until an explicit verification step.
- **Reversibility:** additive contract (version bump `1.1.0 → 1.2.0`), flag OFF
  by default; the migration ships a `down.sql`. Rollback is flag-off or revert;
  the down migration drops only the two new tables and the new enum.
- **Observability:** emits one non-PII event per pass
  (`scout.reconstruct.completed` with `{ intent_id, entity_type, staged,
reconstructed, skipped, failed }`) — no tokens, payloads, names, or email.

## Good without bad

Benefit preserved: a coach's settled crawl becomes an actionable, idempotent,
honestly-counted roster. Failure modes excluded: no auth/credential minted from
unverified data, no email used as a key, no partial roster from a live crawl, no
batch abort from a poison row, no cross-tenant leakage, no PII in telemetry, and
no count that can disagree with durable state.

## Evidence required

- Mapper specs: truecoach client mapped to `{sourcePersonId, sourcePlatform,
displayName}`; non-truecoach platform and empty source_id skipped with a
  reason; email in the payload ignored; never throws (total function).
- Service specs: full accounting (`staged === reconstructed + skipped + failed`)
  over the golden fixture; replay is a no-op (identical counts, no new rows);
  poison row isolated to `failed` while siblings reconstruct; running/unknown
  intent → `409`; the emitted event carries no PII and no email.
- Feature-flag spec: `/api/scout/reconstruct` 404s when `FEATURE_SCOUT_RECONSTRUCT`
  is off (and remains dark while `FEATURE_SCOUT_INGEST` is off).
- Contract: `/scout/reconstruct` added to the frozen slice; byte-identical drift
  test passes against the regenerated `importer-openapi.json` (`1.2.0`).

## Rollback / stop

Unset/`!== 'true'` `FEATURE_SCOUT_RECONSTRUCT` (the default) to dark the route,
or revert the PR and apply `down.sql`. **Stop condition:** if the net-LOC gate
cannot be met in one coherent PR, the feature is marked `[LOC-EXEMPT]` (precedent
#427) with genuine test density ≥ 2.0 rather than dropping tests.

## Deliberate non-goals

- **No claim/link flow.** Attaching an `AuthPrincipal` to a `Person` via a
  credential-verified claim is a separate lane (D2 explicitly scopes it out).
- **No entity family beyond `clients`.** This first proving pass reconstructs
  only `clients`; other families are future passes.
- **No billing data.** Billing remains an excluded data family — never captured,
  staged, logged, or reconstructed.
- **No relabel of the IMPORTER-E status endpoint counts.** Deferred to a
  follow-up to avoid destabilizing the settled status contract; reconstruction
  accounting is delivered via the new endpoint's own response + ledger.
