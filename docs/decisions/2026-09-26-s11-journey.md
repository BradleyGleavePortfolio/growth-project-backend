## 1. Why this exists

PROGRESS L40 names S11 as "Complete customer journey and multi-host integration". JOURNEY L278
defers "multi-host … proof of the whole journey" to S10/S11/S12. The north star is:

- a coach authorizes a source and presses Start **once**;
- then performs **zero routine actions**;
- and sees a **truthful terminal status**.

The existing invariants still hold: no false Complete, unknown is never zero, no duplicate native
identity, no cross-tenant write, no customer-facing side effect during historical reconstruction,
and NEW SOURCE → CORE DIFF = 0.

S7 to S10 built each server step and proved it in isolation, one slice harness at a time.
Nothing yet proves the composed journey when its steps land on different API processes and
client devices, and nothing re-drives a settle interrupted by a process loss (§3 G1).

## 2. Decisions

### D-S11-1: what "multi-host" means for this codebase

"Multi-host" has three concrete axes, each evidenced in source. S11 requires that no state
authority lives in a process, a device or a source origin: PostgreSQL under the run-row lock is
the only authority.

**H-S — several API server processes behind one database.**

- Production runs several Fly machines. Rate-limit state is shared through Redis "across Fly
  machines", and production refuses to boot without it (`src/common/env-validation.ts` L256;
  `src/throttler/throttler.config.ts` L412).
- S7-L already reasons about "an old pod" in a mixed deploy (S7L-DOC L232-238).
- Lifecycle truth is already database-only:
  - Start, cancel, fence and settle lock the run row `FOR NO KEY UPDATE`
    (`src/scout/lifecycle/lifecycle.service.ts` L351-357, L479-482).
  - Every writer passes the SQL gate `assertRunOpen` (L562-572).
  - The deadline is lazy, with "no scheduler, cron or background timer" (S7L-DOC L80-90).
- **Three per-process behaviours exist today:**
  - **(i) The progress snapshot is cached in process.** It is coalesced in a `Map` and flushed
    every 5 s (`src/scout/scout.service.ts` L20-21, L36-43, L69-88, L253-261). A read flushes
    only its own process's keys (L257-261, L427-428).
  - **(ii) Settle runs inline on whichever process received `/complete`.** That process runs
    the reconstruction pass, reconciliation and the terminal CAS inside the request
    (`scout.service.ts` L405-410; `lifecycle.service.ts` L414-445).
  - **(iii) Development falls back to per-process throttling** (`env-validation.ts` L256).

**H-C — two client hosts acting on one intent.**

- The phone uses the coach JWT. It mints the setup (`src/extension-pair/extension-pair.controller.ts`
  L116-119) and reads it back (L167-169, L212-214, L257-267).
- The computer's extension redeems the code, unauthenticated, for a coach-bound session
  (L316-321; `extension-pair.service.ts` L235, L271).
- Both reach the same arbiter, with "no per-device authority" (S7L-DOC L223-224).
- The progress mirror is already keyed per device (`prisma/schema.prisma` L6786-6797).

**H-O — several source origins in one intent.**

- The staged identity key includes `source_platform` (`src/scout/scout-ingest.service.ts`
  L57-67, L90). One intent can therefore stage rows from more than one source.
- `ImportIntent.chosen_platform` is one string (`schema.prisma` L6767). JOURNEY and CQ-06 treat
  it as a shortcut label, not the authorized scope, and the DTO says as much
  (`extension-pair.dto.ts` L122-125).
- The authorized per-platform scope is the S10 run declaration (S10-DOC D-S10-2).

**Decision.** S11 proves the journey across all three axes at once:

- two independent server processes;
- two client roles (phone, extension) of one coach, and a second coach;
- a two-platform declaration.

The S11 real-PG proofs are **cross-process service and database composition**. Their workers
call the services directly with a supplied coach id (`test/utils/g2-s9c-worker.cjs` L54-76,
L181-215), so they do not prove H-C authentication. That boundary is:

- the phone JWT and the redeemed extension session both authenticate;
- both guards resolve to the same coach.
  It stays with the existing accepted route and guard specs, which S11 cites and does not re-prove:
- `src/extension-pair/__tests__/{extension-pair.controller,extension-pair.controller-wiring,`
  `auth-mint-extension-session,coach-guard-role}.spec.ts`;
- `test/auth/extension-auth.spec.ts`;
- `test/scout/lifecycle/run.controller.spec.ts`.

It changes behaviour only where an H-S per-process behaviour can make the terminal untruthful
or unreachable (G1). The other per-process behaviours are accepted as mirror-only and are bounded
by tests (D-S11-3).

### D-S11-3: gaps and their disposition

**G1 (A for the north star) — a settle interrupted by process loss cannot be re-driven.**

- **Symptom.** The claim transaction commits and moves the phase to `reconciling`
  (`scout.service.ts` L375-392). The pass then runs in the same request (L410).
- If that process dies or is redeployed mid-pass, "an unexpected pass failure … leaves the run
  open for the lazy deadline" (`lifecycle.service.ts` L404-406).
- A retried `/complete` hits the completion-ledger unique and returns `ack` **without settling**
  (`scout.service.ts` L399-401). The run can then only end `timed_out`, even though the whole
  transfer arrived. That outcome is truthful but violates "press Start once, zero routine
  actions".
- **Disposition: S11-B** (D-S11-4).

**G2 (C) — the progress mirror is per process (H-S (i)).**

- A status read on process B cannot flush a snapshot pending on process A. The mirror can
  therefore be up to one flush interval (5 s) stale, and it is lost if A dies before flushing.
- The truth fields do not depend on it:
  - the terminal, phase and `last_observed_at` are written in the gated request itself
    (`scout.service.ts` L130-134, L143-155);
  - the counts come from persisted rows (L414-418).
- **Disposition:** accepted, mirror-only. S11-A asserts a cross-process read bound. No code
  change.

**G3 (B) — the phone cannot see "source declared" or run linkage from the setup read.**

- `readSetup` returns only `status`, `import_intent_id` and `chosen_platform`
  (`extension-pair.service.ts` L195-221).
- CQ-08 asks for readiness ("source account confirmed"). After S10-B, the declaration exists
  but nothing exposes it.
- **Disposition: S11-C**, an additive read-only `readiness` block (D-S11-5).

**G4 (B, owner) — one immutable deadline covers transfer and settle.**

- `deadline_at = accepted_start_at + SCOUT_RUN_DEADLINE_MS`, with a default of 300 000 ms that
  is never updated (`lifecycle.service.ts` L69-72, L260-261; S7L-DOC L80-84).
- Every per-row reconstruction transaction re-checks `deadline_at > now()` (L569). Transfer
  plus settle must therefore finish inside one window, or the run ends `timed_out`.
- **Disposition:** S11 keeps D-S7L-3 unchanged. Proofs set the environment value explicitly.
  The production value, and whether a renewable lease is wanted, are owner question Q-S11-1.

**G5 (C) — the coach push is keyed to the extension claim, not the server verdict.**

- `notifyComplete` runs before `onTransferSettled` (`scout.service.ts` L405 then L410). Its copy
  already says "Migration is not verified" (L553-561).
- A run that ends by deadline or cancel sends no push.
- **Disposition:** no change in S11. The copy and a verdict-keyed push belong to the copy owner
  (UX-05, CQ-17). The push goes only to the importing coach, never to that coach's clients, so the
  side-effect invariant is untouched (S8-DOC D-S8-4 L104 and §3.6 L223 suppression stays).

**G6 (C) — `chosen_platform` versus a multi-origin run.**

- Ingest does not check `source_platform` against the setup label (`scout-ingest.service.ts`
  L90).
- S10's evaluator already makes undeclared-but-staged platforms `known: false` (S10-DOC
  D-S10-3 E1).
- **Disposition:** no code. S11-A proves that a two-platform declared run can be `complete`,
  and that a run whose second platform is staged but undeclared is `partial`.

**G7 (process) — each proof forks roughly 1,200 lines of harness.**

- `test/utils/g2-<slice>-{bootstrap.sh,db,harness,pg-harness}.ts,worker.cjs` is copied "by
  literal substitution" per slice (`test/utils/g2-s9c-pg-harness.ts` L2-3;
  `g2-s9c-worker.cjs` L1-10).
- **Disposition:** D-S11-6.

**G8 (B) — consumers need one frozen contract.**

- Extension and mobile consume the generated importer artifact (S7L-DOC L246-249).
- S10-C regenerates it once. S11-C adds one additive block.
- **Disposition:** the generator owner regenerates once in S11-C. The consumer builds are out
  of repository and reserved (§7).

The extension-side items stay reserved (§7): capability and version negotiation (CQ-09), store
identity (CQ-07) and extension disconnect (CQ-15).

### D-S11-4 (G1): re-drivable settle, no new route

- A replayed `POST scout/ingest/complete` for a server run re-drives
  `onTransferSettled(coach, intent, epoch)` when all of these hold:
  - the run is open (`terminal_status IS NULL`);
  - it is not fenced;
  - its phase is `reconciling`;
  - a completion row exists (the P2002 branch, `scout.service.ts` L399-401).
- `epoch` is re-read under the gate in the replay's own short transaction, never taken from
  the client.
- The stored claim is **never** overwritten: the first claim stays the arbiter input
  (S7L-DOC L74-77). A replay with a different `terminal_status` is still only a
  trigger.
- The re-drive is safe because the settle is already CAS-guarded and replay-safe:
  - the pass is gated per row and CAS-checked on `epoch`;
  - ledger and provenance keys are unique, so a re-run writes no duplicate (S8-DOC; invariant
    3 of S10-DOC D-S10-6);
  - the terminal is one CAS (`lifecycle.service.ts` L437-438).
- Two concurrent re-drives on two processes each run the pass, and at most one CAS wins. The
  loser is the existing "a miss is not an error" path (L403-404).
- **No new push or analytics event on a re-drive.** `notifyComplete` and
  `SCOUT_INGEST_COMPLETED` stay first-claim-only (L405-409).
- **What is rejected, and why:**
  - A status read triggering settle: this is heavy work on a read, and it multiplies across
    phone polls.
  - A background re-drive: PLAN decision 6 and S7L-DOC L89-90 forbid a timer owner.
  - A new `/settle` route: this adds contract surface for the same behaviour.
- A dead extension is still ended truthfully by the lazy deadline.
- **Owned code:**
  - `src/scout/scout.service.ts`: the P2002 branch and a private re-drive helper, about 40
    product lines;
  - `src/scout/lifecycle/lifecycle.service.ts`: at most one read helper, `isReDrivable`. This
    runs only after S10-C lands, because S10-C owns that file until then.

### D-S11-5 (G3): an additive readiness block on the setup read

`PairSessionResult` (`extension-pair.dto.ts` L114-126) gains an optional `readiness` object,
returned by `pair/session` and `pair/current` only:

```ts
readiness?: {
  run: 'none' | 'open' | 'terminal';   // from ScoutImport by import_intent_id; no terminal detail
  source_declared: boolean;            // ≥1 ScoutRunDeclaration row for the run (S10-B)
  declared_platforms: number | null;   // count only; null when run === 'none'
}
```

- The block is read-only and uses the caller's `coach_id` (the existing `readSetup` owner filter,
  L199-201). It exposes no scope digest, challenge or platform names.
- Terminal status and reason codes stay on `GET scout/import/status`, the single read of truth
  (S7L-DOC §5).
- It exists so the phone can render J6 without guessing.
  - Display semantics are neutral: `source_declared: true` may read "declaration received",
    and never "source authorized", "source ready" or "connected".
  - `source_declared` means only that a coach-scoped declaration row exists. Real source
    authorization stays **unknown** until the owner-reserved verifier and principal policy
    exist (S10 Q2/Q5, G3-AUTH).
  - Absence means "not known" and is never shown as "no".
- **Owned code:** `src/extension-pair/extension-pair.{service,dto}.ts`, about 60 product lines.
  The contract is regenerated once by the generator owner.

### D-S11-7: multi-host invariants (asserted by S11 specs; all S7–S10 invariants unchanged)

1. **The database is the sole authority.** No terminal, phase, epoch, deadline, claim,
   declaration or evidence decision depends on process memory, device identity or the setup's
   `chosen_platform` label.
2. **One run per intent, one terminal per run.** Any interleaving of Start, ingest, progress,
   observation, claim, replayed claim, cancel and status reads across two processes and two
   client principals yields exactly one terminal write (S7L-DOC D-S7L-2).
3. **Replay is idempotent.** Replaying any step from any host (Start, a batch, an observation, a
   claim) creates no second run, native row, provenance row, claim, push or terminal.
4. **Unknown is never zero across hosts.** A missing mirror snapshot, an unflushed cache or an
   absent declaration is `null`, `none` or `false`, never 0 or `complete`.
5. **Tenant isolation.** A second coach's concurrent journey on the same two processes can
   neither read nor change the first coach's intent, run, declaration, observation or native
   rows. This is a no-foreign-access property, not one response code on every route:
   - routes whose accepted contracts answer 404 for a foreign or unknown intent keep that
     uniform 404 (setup reads, `runs/start|cancel`, reconstruct reads). `import/status` answers
     404 for a foreign intent only while coach B has no evidence of its own under that string;
   - `POST scout/progress` keeps its accepted 204 (`scout.controller.ts` L66-85;
     `scout.service.ts` L125-155). A UUID owned by coach A resolves as legacy for coach B
     (`lifecycle.service.ts` L221-241), so B's snapshot is cached and flushed under B, with no
     ingest-row FK (`scout.service.ts` L143-173, L197-225). B's `import/status` may then read that
     B-owned snapshot (L427-457). This is accepted behaviour and not a leak, because nothing of
     coach A's is written, cached or disclosed;
   - legacy (non-UUID) intent strings keep their legacy semantics and are asserted separately.
6. **No customer-facing side effect.** No notification, drip, email or message reaches a
   coach's client during steps 5 to 8. The only push is the existing coach-directed
   `import.complete` (`scout.service.ts` L563-567), once per run.
7. **CORE DIFF = 0 holds across the journey.** No S11 file keys on a platform slug. The journey
   proof runs on the synthetic `s10_unseen` source together with a second synthetic source
   (S10-DOC D-S10-5).

## 3. Acceptance cases (J-cases; real PG unless marked "unit")

Two worker processes (P1, P2) run over one disposable PG. They are direct-service workers
acting for coach A with a supplied coach id (D-S11-1). "phone" and "ext" label which client
role a step stands for; they are **not** authenticated principals. Coach B runs concurrently.

- **J01 (A1)** Setup to Start across processes, at the service level. The steps are the
